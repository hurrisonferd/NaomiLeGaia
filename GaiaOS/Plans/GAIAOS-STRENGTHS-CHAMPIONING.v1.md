## Purpose

Turn GaiaOS's demonstrated strengths into explicit architectural selection pressure.

Future work should not merely avoid regressions. It should preferentially deepen the properties that make GaiaOS coherent.

## Primary strengths

### A. Epistemic separation
Champion architectures that keep these dimensions distinct:

```text
IMPORTANCE != AUTHORITY
RELEVANCE != AGREEMENT
RELATION != CAUSATION
HISTORY != CURRENT GOVERNANCE
REVISES != SUPERSEDES
SUPERSEDED != ERASED
STORAGE PRECISION != EPISTEMIC PRECISION
REQUESTED != COMPLETED
SOURCE != DEPLOYED
DEPLOYED != OBSERVED
OBSERVED != GENERALLY PROVEN
```

Any new subsystem or feature that collapses two of these must justify the collapse with explicit evidence and Naomi authorization.

### B. Query-first contextual intelligence
The query/context gate determines candidate existence. Adaptive influence operates only after admission.

```text
RELEVANCE -> ELIGIBILITY -> CONTEXTUAL MODIFIERS -> RANKING -> RETRIEVAL
```

No importance, graph centrality, recency, personality preference, or prior success signal may summon an otherwise irrelevant candidate into ordinary retrieval.

### C. Temporal memory semantics
Preserve historical authenticity while separately representing current governing state.

Prefer:
- revision edges;
- supersession edges;
- governing-state flags;
- lifecycle attenuation;
- reversible archival;
- reactivation through new evidence.

Avoid destructive rewriting as the default update mechanism.

### D. Negative-evidence intelligence
Treat these as first-class inspectable state:
- failed proofs;
- HOLD;
- ambiguity;
- rejected candidates;
- stale state;
- superseded history;
- contradictory evidence;
- non-occurrence;
- reasons a proposal did not advance.

Success-only histories are considered lossy.

### E. Differentiated multi-perspective continuity
Shared events may produce multiple member-local interpretations.

```text
SHARED EVENT != SHARED MEMORY
DELIBERATION != CONSENSUS
DIFFERENCE WITH CONSEQUENCE -> PRESERVE
NO CROSS-MEMBER IDENTITY MERGE
```

VASKON should increase useful cross-lane exchange without flattening Prime Daemon identities.

### F. Precision over proliferation
New OS/subsystem creation is not itself progress.

Before creating a new subsystem, test whether:
1. an existing owner can express the function cleanly;
2. the proposed function has a distinct ontology;
3. it requires a distinct authority boundary;
4. it has a distinct lifecycle or proof contract;
5. composition would be clearer than extension.

If not, extend the existing owner.

### G. Explainable adaptation
Adaptive systems should be able to expose:
- why something appeared;
- which gate admitted it;
- which modifier changed its rank;
- which provenance supports it;
- which governing state applies;
- what uncertainty remains.

Human-facing explanation should be progressively disclosed, not dumped by default.

### H. Reversible power
Prefer changes that can be:
- inspected;
- attenuated;
- superseded;
- rolled back;
- replayed;
- compared against control.

Irreversible effects require a higher proof and authorization threshold.

## Current build application

For the remaining GALAXY phases:
- Phase 3 must compare weighted retrieval against an unweighted control.
- Gravity may rerank only already-relevant candidates.
- Explanations must preserve query relevance separately from modifier contribution.
- Low-gravity but highly relevant records must have starvation tests.
- Failed reranking experiments remain evidence.
- Phase 4 revision/supersession must preserve historical state and governing-state distinction.
- Phase 5 synthesis must retain source provenance and dissent.
- Phase 6 attenuation must be reversible.
- Phase 7 pruning remains research-only until deletion authority is separately designed and proven.

## Future build application

Future Semantic Conservation, capability discovery, loadout, VISOR, portability, and carrier work should inherit the same strengths.

Required inheritance:
- semantic class does not drift during transformation;
- capability availability does not become authorization;
- selected tools do not become authority;
- portability does not become identity transfer;
- successful execution does not become causal proof;
- rejected alternatives remain inspectable when materially useful;
- human-facing surfaces compress complexity without hiding evidence ceilings.

## Build review checklist

Before promoting a new feature, ask:

1. Which distinctions does this feature preserve?
2. Can it inflate authority?
3. Can it manufacture relevance?
4. Can it erase historical or negative evidence?
5. Can it merge identities or ownership lanes?
6. Is its effect reversible?
7. Is there an unchanged control or baseline?
8. Does it produce a receipt or observable proof?
9. Can a fresh carrier determine the true current state from canonical pointers?
10. Does this deepen an existing GaiaOS strength, or merely add machinery?

## Anti-patterns

Reject or redesign:
- authority hidden inside scores;
- recommendation hidden inside retrieval;
- retrieval hidden inside identity;
- currentness hidden inside importance;
- failure hidden by narrative cleanup;
- stale canonical pointers;
- synthetic consensus;
- subsystem proliferation without ownership need;
- adaptive loops without controls;
- irreversible forgetting before reversible attenuation is exhausted.

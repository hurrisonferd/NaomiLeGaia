# GaiaOS integration: normal Render startup and isolated chat during MemconOS outage

SOURCE-ONLY STACKED DRAFT on PR #113. No main merge, Render deploy, user data, real Turso connection or credential, owner cutover, production BIGBANG activation or modification of the existing RavenOS bridge. Tests are isolated, use dummy credentials and offline fake provider responses.

## Concrete source failures repaired

The actual Render Docker CMD starts browser_memcon_bridge, which imports memcon_entrypoint. Before this fix, memcon_entrypoint eagerly called memcon_runtime.initialize() while importing the app. If the configured original GaiaOS Turso backend or driver were unavailable, the normal carrier process could crash before FastAPI served even /health or the HEATDEATH original hosted-chat path. An independent read-only legacy recovery app exists, but it is NOT the same as a working normal GaiaOS carrier.

This patch removes only the eager database initialization. Normal memory endpoints retain their original on-demand runtime initialization, storage schema and owner-authorized write gates. The app never silently falls back from unavailable Turso to an empty local SQLite file. It continues to report the configured backend and safeguards separately from carrier liveness.

The actual browser bridge checks get_solo_session before it dispatches ordinary requests. After the eager-init repair, a memory outage could still crash this lookup or tempt an unsafe generic-chat fallback. If SOLO state is unavailable, the normal /chat route now returns HOLD_SOLO_STATE_UNVERIFIED without leaking records, error messages or pretending that a possibly active SOLO session has ended. It cannot independently prove generic mode while that state is inaccessible.

A separate /chat/recovery POST route serves the existing baseline hosted model ONLY after an explicit acknowledgment, an explicit include_memory=false flag, a single NEW user message with NO previous conversation history, and the pre-existing signed browser-session check. It never calls MemconOS, the mode controller, GALAXY or SOLO state. It does not release memory, promote records, create E-LANE writes, resume Daemons or repair storage. Existing model presentation/source validation still applies, so it must not invent attributed Daemon speech. A matching GET page provides an accessible phone-browser form with a required acknowledgment; normal home displays a meaningful recovery URL upon a SOLO-uncertain HOLD rather than showing [object Object]. Recovery is a deliberately separate generic conversation, not implicit normal-chat failover.

IMPORTANT AUTHENTICATION BOUNDARY: this preserves GaiaOS's current signed browser cookie behavior, including its public home-page session bootstrap. A valid cookie proves only server signature, NOT independent human ownership. It must not be claimed as owner authentication for a production SovereignOS launch. This draft does not change or harden the existing owner-login architecture and must not be used to infer independent SOS access control.

The existing /memconos/health route previously returned durable_backend=true and a local DB path even when running ephemeral SQLite. It now checks the actual selected backend with a fresh SELECT, returns redacted HOLD with HTTP 503 if unavailable, and never leaks DB path, remote URL, token or low-level exception string. A successful SELECT reports storage_reachable=true but leaves durable_backend, durability_verified and restart_canary_verified FALSE until distinct, independently observed post-restart proof. Carrier /health remains DB-independent and must never be used as memory durability evidence.
